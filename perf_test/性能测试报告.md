# 项目管理系统接口性能测试报告

| 项目 | 内容 |
|---|---|
| 被测系统 | 测试平台「项目管理」REST 接口 |
| 测试类型 | 负载测试（Load Test）+ 阶梯加压 + 瓶颈定位与调优 |
| 测试工具 | Locust（压测）、psutil（服务端资源监控）、自研三层拆解脚本 |
| 报告日期 | 2026-09-14 |

---

## 一、结论摘要

在**万条数据量**下对项目列表接口做阶梯加压，发现两个真实瓶颈。完成定位与优化后：

| 指标（100 并发） | 优化前 | 优化后 | 提升 |
|---|---|---|---|
| 吞吐量 TPS | 5.7 | **45.8** | **8.0 倍** |
| 平均响应时间 | 12,848 ms | **19 ms** | **686 倍** |
| P95 响应时间 | 24,000 ms | **53 ms** | **453 倍** |
| 失败率 | 14.7% | **0%** | 消除 |
| 服务端 CPU 占用 | 151% | **35%** | 处理更多请求，反而省 3/4 CPU |
| 平均响应体 | ~1,002 KB | **14 KB** | 缩小 99% |

**一句话总结**：优化前，100 个并发用户就能把系统压到反向伸缩（人越多吞吐越低）并产生 14.7% 的服务端错误；优化后，同一接口在 **400 并发下仍保持 0% 失败率，吞吐随并发线性增长**，且尚未触及容量上限。

优化后仍用原有的 **44 条接口自动化用例做了回归验证，全部通过**，确认性能优化未破坏接口功能契约。

---

## 二、测试目标

1. 量化接口在真实数据量下的性能表现，找出**容量拐点**（从正常到劣化的转折点）。
2. 定位瓶颈的**具体位置**，而不是停留在"系统慢"这种结论上。
3. 实施优化并用同一套方法复测，给出**可对比的前后数据**。
4. 用功能回归用例验证优化**没有破坏既有契约**。

## 三、被测系统

```
┌──────────────────────────────────────────────┐
│  被压测对象：项目管理系统 REST 接口           │
│    GET    /api/projects/        查询列表      │
│    POST   /api/projects/        新建项目      │
│    GET    /api/projects/{id}/   查询详情      │
│    PUT    /api/projects/{id}/   更新项目      │
│    DELETE /api/projects/{id}/   删除项目      │
└──────────────────────────────────────────────┘
        Django 6.1 + SQLite + 开发服务器(runserver)
```

### 为什么给这个接口做性能测试

它原本是作为**接口自动化框架的被测对象**存在的，最初只有 2 条数据，功能测试全部通过 —— 但功能正确不等于性能合格：

> 列表接口的实现是把**整张表**一次性查出来返回，没有分页。
> 库里 2 条时毫无问题；涨到 1 万条后，每次请求都要实例化 1 万个 ORM 对象、构造 1 万个字典、序列化出 1.5 MB 响应体。
> **功能测试永远发现不了这个问题，因为它只是慢，没有错。**

要让这个问题浮现出来，必须先造出足够的数据量，这就引出了下一节的方案设计。

## 五、测试方案

### 5.1 场景设计：混合操作，而非单接口压测

只反复调一个接口叫**基准测试（benchmark）**，测不出"真实场景下系统能扛多少"。真实用户是混合操作的 —— 大部分时间在看（查），偶尔写（增删）。

因此按真实使用频率分配权重：

| 操作 | 权重 | 占比 | 说明 |
|---|---|---|---|
| 查询列表 | 11 | 55% | 最常用的操作，重点观察对象 |
| 查询详情 | 5 | 25% | 模拟点击进入某个项目 |
| 新建项目 | 2 | 10% | 写操作 |
| 删除项目 | 2 | 10% | 写操作 |

**为什么增删配成 1:1**：写操作只增不减的话，数据库会随压测时间不断膨胀，第二轮压测的起点就与第一轮不同，结果无法复现。让增删互相抵消，**压测才具备可重复性**。

### 5.2 思考时间：负载测试而非压力测试

每个虚拟用户执行完一个操作后，随机等待 1~3 秒再做下一个，模拟真人"看一眼、想一下、再点"的节奏。

- **加等待时间** → 测的是**真实负载**下的表现（Load Test）
- **不加等待时间** → 测的是**极限承压能力**（Stress Test）

本报告测的是前者。

### 5.3 数据准备

用一个批量造数据脚本，以 `perf-seed-` 为前缀灌入 10,000 条数据：

```
批量插入（bulk_create，每批 1000 条）  →  约 5 万条/秒
逐条插入（循环 .create()）            →  几十秒才完成
```

> 这是 Django 中最常用也最常被面试问到的性能技巧：**批量写比逐条写快两个数量级**，因为前者把 N 次 INSERT 和 N 次事务合并成了少量批量操作。

### 5.4 安全设计：压测脚本绝不能删到真实数据

压测脚本包含删除操作，一旦设计不当，就可能在压测过程中删掉业务数据。采用**双前缀 + 每用户私有池**方案：

| 前缀 | 用途 | 是否会被删除 |
|---|---|---|
| `perf-seed-` | 种子数据，撑起"大数据量"这个条件 | **永不删除** |
| `perf-load-` | 压测过程中虚拟用户自己建的 | 由创建者自己删 |

两条铁律：

1. **删除范围严格限制在"本虚拟用户自己造的"**（每个用户一份私有 id 池，不存在跨用户竞争）。真实数据不在任何人的池子里，因此永远不会被删到。
2. **读池里的 id 必须保证活着**，预热时只收 `perf-seed-`，把随时会被删的 `perf-load-` 排除在外。

> 第 2 条是踩坑踩出来的：早期两批数据用同一个前缀，结果 100 并发时冒出 3.4% 的假 404。根因很隐蔽 —— **后启动的虚拟用户，会捞到先启动用户建的、稍后会被删的数据**。
> 教训：压测脚本里的"假失败"最危险，它不会让测试崩掉，只会悄悄把错误率抬上去，让人误判成服务端有问题。

**验证结果**：经过 6 轮压测，累计创建/删除压测数据 11,311 条，业务数据 `(2, '111')`、`(3, 'demo-project')` 一条未动。

### 5.5 监控指标

只看压测工具的输出是不够的，还要同时盯住服务端：

| 指标 | 含义 |
|---|---|
| TPS | 吞吐量，每秒处理请求数 |
| 平均响应时间 | 所有请求的平均值 |
| **P95 / P99** | 95% / 99% 的请求在此时间内完成 —— **比平均值更能暴露长尾问题** |
| 失败率 | 错误请求占比 |
| **服务端 CPU** | 判断瓶颈性质的关键指标（见下） |

> **为什么必须看 CPU？**
> 只压测、不看服务端状态，等于医生只看病人喊疼、不量体温。
> - CPU 打满 → 瓶颈在**计算**（如序列化、加密）
> - CPU 不高但很慢 → 瓶颈在**等待**（如数据库锁、磁盘 I/O、网络）
>
> 这两种情况要采取的优化手段完全不同。本案例中正是 CPU 的异常表现指引我们找到了真正的根因。

### 5.6 开跑前的环境体检

压测脚本在启动前会自动确认：**8000 端口只有一个进程在监听**；若发现多个，直接拒绝执行并提示清理。

> 这道检查是踩坑之后加的。Windows 允许两个进程绑定同一端口，一旦发生，请求被分给谁是不确定的，采出来的数据无法解释。**数据干净比跑得快重要得多** —— 详见附录 A。

## 六、优化前的测试结果

**数据量：10,019 条** | 每档持续 60 秒

| 并发 | 请求数 | 失败数 | TPS | 平均(ms) | P95(ms) | P99(ms) | 平均响应体 | 服务端CPU |
|---|---|---|---|---|---|---|---|---|
| 10 | 275 | 0 | 4.6 | 83 | 190 | 240 | 897 KB | 28% |
| 50 | 460 | 23 | 7.7 | 3,627 | 11,000 | 13,000 | 963 KB | 155% |
| 100 | 339 | 50 | 5.7 | 12,848 | 24,000 | 26,000 | 1,002 KB | 151% |

失败率：0% → 5.0% → **14.7%**

### 三个异常信号

1. **反向伸缩（thrashing）**：并发从 10 涨到 100（10 倍），TPS 只从 4.6 涨到 5.7，而且中途在 50 并发达到 7.7 之后就开始**回落**。
   正常系统应该是"随并发上升、到某个拐点后才饱和"；这里却是过了某个点就越压越差，说明请求之间在**互相拖累**。
2. **CPU 上不去**：服务端 CPU 停在 150% 左右（机器有 16 个逻辑核），远远没吃满。
   **这不是"算不过来"，而是"在等"** —— 这是锁竞争的典型特征。
3. **出现服务端错误**：服务端日志中统计到 **101 次 `django.db.utils.OperationalError: database is locked`**，对应 **73 个 HTTP 500**。

## 七、瓶颈定位：三层拆解法

压测只能告诉你**慢**，告诉不了你**慢在哪**。为了把"猜"变成"量"，把一次请求从"纯计算"到"完整走网络"分成三层分别测量：

| 层次 | 测量方式 | 优化前耗时（10,019 条） |
|---|---|---|
| 第 1 层 纯计算 | 直接调 ORM + 转字典 + 序列化，不起服务器 | **78 ms** |
| 第 2 层 Django 请求处理 | 用测试客户端走完整中间件/视图，不走网络 | **85 ms** |
| 第 3 层 真实 HTTP | 打真实服务器，测 TTFB 与总耗时 | TTFB **112 ms**，总 **116 ms** |

第 1 层内部拆解：

```
① 查数据库 + 建 ORM 对象   46 ms
② 逐条转成字典 to_dict()   25 ms
③ 序列化成 JSON 文本        7 ms
────────────────────────────────
合计                       78 ms   （10,019 条，1,485 KB）
```

**三层数据自洽**，每一层的差额都能归因：

```
第 2 层 - 第 1 层 =  7 ms   → 中间件 / 请求构造 / 响应构造
第 3 层 - 第 2 层 = 27 ms   → WSGI 服务器 + TCP
传输耗时 = 总耗时 - TTFB = 4 ms
```

### 关键排除：不是"传 1.5 MB 太慢"

一个自然的猜想是"响应体 1.5 MB，传输花了不少时间"。用**控制变量法**排除：让同一台服务器吐一个大小几乎相同的静态文件。

| 请求 | 响应体大小 | TTFB | 总耗时 |
|---|---|---|---|
| 静态文件 `styles.css` | 1,525,056 字节 | **5.5 ms** | **54 ms** |
| `/api/projects/` | 1,520,565 字节 | **450 ms（当时读数）** | 470 ms |

**同样 1.5 MB，静态文件 54 ms 就发完了。** 说明：
- 传输本身不是瓶颈（TTFB 占了总耗时的绝大部分）
- 数据量大本身也不是原因 —— 原因在于**处理这些数据所花的计算量**

至此瓶颈锁定：**每次请求都要为整张表做一遍全量计算，而这个成本随数据量线性增长。**

## 八、根因分析

### 瓶颈一：列表接口没有分页，成本随数据量线性增长

```python
# 优化前的实现
projects = [p.to_dict() for p in Project.objects.all().order_by("id")]
return JsonResponse(projects, safe=False)
```

- 每次请求都要实例化**全部** 10,019 个 ORM 对象
- 每次请求都要构造 10,019 个字典并序列化 1.5 MB
- **成本与表大小成正比** —— 数据越多越慢，这是一个会持续恶化的问题，不会自愈

### 瓶颈二：SQLite 写锁 —— `database is locked`

服务端日志中 101 次锁错误，根因在于 **Django 默认使用 `DEFERRED` 事务**：

SQLite 的事务有三种开始方式：

| 模式 | 行为 |
|---|---|
| `DEFERRED` | **Django 默认**。先按「读」事务开始，等第一条写语句时才尝试升级成写锁 |
| `IMMEDIATE` | 一上来就要写锁，拿不到就等 |
| `EXCLUSIVE` | 排斥所有其他连接 |

**坑就在 `DEFERRED` 上**：如果两个事务都先读了数据、然后都想写，此时它们的读事务要升级成写事务 —— 这是**无法安全完成的**（互相都在等对方释放读锁）。SQLite 判断存在死锁风险，于是**直接返回 `SQLITE_BUSY` 报错，根本不提供等待重试的机会**。

> 所以哪怕把 `timeout` 设得再大，在这种场景下也照样报 `database is locked`。

同时，SQLite 默认使用 rollback journal 模式：**写的时候整张库会被锁住，连读都要排队**。

**这解释了压测中观测到的全部现象**：CPU 上不去（在等锁而不是在算）、TPS 反向伸缩（请求互相阻塞）、高并发下大量 500（锁冲突直接报错）。

## 九、优化措施

### 优化一：列表接口分页

```python
DEFAULT_LIMIT = 100      # 默认返回 100 条
MAX_LIMIT = 1000         # 服务端强制上限

limit, offset = _parse_paging(request)
queryset = Project.objects.all().order_by("id")
total = queryset.count()
projects = [p.to_dict() for p in queryset[offset:offset + limit]]

response = JsonResponse(projects, safe=False)
response["X-Total-Count"] = total
return response
```

三个设计决策及其理由：

**1. 上限必须由服务端说了算。**
如果允许客户端传 `?limit=999999999`，等于把分页关掉了 —— 只要有一个调用方这么干，数据库照样被打穿。性能优化的基本原则：**把安全的选择设成默认值**，让需要大量数据的人显式声明意图。

**2. 默认值设成 100，而不是"默认全给、要分页自己传"。**
因为"默认全给"意味着**默认行为就是最危险的那个**。

**3. 响应体仍保持 JSON 数组，总数用 `X-Total-Count` 响应头返回。**
既有 44 条接口用例依赖 `isinstance(response.json(), list)`，改成 `{"count":…,"results":[…]}` 会让这批用例全挂。
**这正是回归测试存在的意义**：它逼你在改接口时想清楚"这个改动会破坏谁"，而不是想改就改。用响应头传总数是 REST 中常见的折中做法 —— 既保住响应体结构，又不丢信息。

**边界处理**（越界值一律夹回合法范围，非法输入不报错）：

| 输入 | 实际行为 |
|---|---|
| `?limit=3&offset=5` | 返回第 6~8 条，顺序正确 |
| `?limit=999999999` | 夹到上限 1000 条 |
| `?limit=0` / `?limit=-1` | 夹到下限 1 条 |
| `?limit=abc` / `?offset=abc` | 用默认值，返回 200 而非 500 |
| `?offset=-5` | 夹到 0 |

### 优化二：SQLite 事务与日志模式调优

```python
"OPTIONS": {
    "timeout": 20,                    # 等锁最多等 20 秒（默认 5 秒）
    "transaction_mode": "IMMEDIATE",  # 事务一开始就拿写锁
    "init_command": "PRAGMA journal_mode=WAL; PRAGMA synchronous=NORMAL;",
}
```

| 参数 | 作用 |
|---|---|
| `transaction_mode="IMMEDIATE"` | **关键修复**。事务开始时就获取写锁，避免 `DEFERRED` 的升级死锁问题；冲突从"当场报错"变成"排队等待" |
| `timeout=20` | 配合上一条生效，等锁最多等 20 秒 |
| `journal_mode=WAL` | 读写不再互相阻塞（默认模式下一次写入会锁住整张库） |
| `synchronous=NORMAL` | 配 WAL 的常用组合，写入显著提速；代价是断电时最多丢失最后一个事务 |

**验证优化已生效**（从 Django 自身的数据库连接查询，因为 `synchronous` / `busy_timeout` 是每连接属性）：

```
journal_mode   = wal
synchronous    = 1      (NORMAL)
busy_timeout   = 20000  ms
```

**更能说明问题的是"每单位 CPU 的吞吐"**：

```
优化前：5.7 TPS ÷ 151% CPU = 0.038 TPS / 每百分点 CPU
优化后：45.8 TPS ÷ 35% CPU = 1.31  TPS / 每百分点 CPU
                          ≈ 34.7 倍
```

优化前把大量 CPU 花在了**锁等待与重试**上；优化后 CPU 真正用在了处理请求上。

## 十一、功能回归验证

性能优化必须证明**没有破坏功能**，否则优化没有意义。用原有的 44 条接口自动化用例做回归：

```
44 passed in 0.92s
```

全部通过。

> **一个值得注意的细节**：这 44 条用例中本来就有**一条性能底线用例** ——
> ```python
> assert response.elapsed.total_seconds() < 1   # 列表接口必须 1 秒内返回
> ```
> 它单线程跑一直是过的（优化前 112 ms，优化后 8 ms），但它**完全测不出并发下的问题** —— 同一个接口在 100 并发时 P95 是 24 秒。
> **功能测试里的性能断言 ≠ 性能测试。** 它能守住"单次调用不能太离谱"这条底线，但无法替代在真实并发下测量系统行为。

## 十二、遗留问题与后续方向

本报告不把结论说成"问题已彻底解决"。以下是明确的局限：

| # | 遗留问题 | 说明与建议方向 |
|---|---|---|
| 1 | **SQLite 仍只允许单写者** | WAL 解决了"读写互堵"，但没解决"写与写互斥" —— 任何时刻仍只有一个写事务。本案例是读多写少（读 80% / 写 20%）所以收益极大；若是写密集场景，必须换 PostgreSQL |
| 2 | **深分页仍然低效** | `?offset=100000` 需要先扫过前 10 万行再丢弃，成本随 offset 增长。根治方案是**游标分页（keyset pagination）**：用 `WHERE id > 上一页最后一条` 代替 `OFFSET` |
| 3 | **容量上限未测出** | 400 并发时 CPU 136%（16 核），仍未饱和。但压测工具与服务端同机，再往上加压时 **Locust 自身会先成为瓶颈**。需要分布式压测或独立压测机才能得到准确容量 |
| 4 | **接口契约仍是"数组 + 响应头"** | 更规范的做法是返回带分页元信息的对象（`count` / `next` / `previous`），但那会破坏现有调用方。应作为 v2 接口推进，并给客户端留迁移期 |
| 5 | **未做缓存** | 列表首页是典型的高频只读请求，适合加缓存。但需先想清楚失效策略（写操作后如何失效），否则会引入数据不一致 |
| 6 | **开发服务器不是生产服务器** | `runserver` 是单进程多线程的调试用服务器，其并发能力远低于 gunicorn/uWSGI。本报告的数据用于**横向对比优化前后**是有效的，但不能当作生产容量指标 |

## 附录 A：一次测试环境事故的记录

**现象**：同一接口的真实 HTTP 请求耗时 450~620 ms，但代码内部三层拆解只算出 78~85 ms。中间 400 多毫秒凭空消失，反复检查代码找不到原因，一度怀疑是 JSON 序列化器的选型问题（专门做了对照测试，三种序列化方式均为 7~9 ms，排除了该猜想）。

**根因**：测量环境的进程归属不清晰。启动一个 Django 服务，系统里会同时出现多个相关进程（外层 shell、venv 启动器、真正干活的解释器），仅凭命令行字符串去数进程会得出错误结论。**当时实际上是在用"进程 A 的代码耗时"去解释"另一个上下文的响应时间"。**

**处理**：清掉多余进程、只保留一个干净的服务后重测，三层数据立即自洽（78 ms / 85 ms / 112 ms），并把这个事故变成了一条改进措施：

> 压测脚本现在会在开跑前自动确认「8000 端口只有一个进程在监听」，否则拒绝执行。

**教训（两条）**：
1. **测量之前先确认"被测对象是唯一且明确的"** —— 否则数据再漂亮也没有意义。
2. **分层测量本身就是最好的排错手段** —— 它把"猜"变成了"量"。同一轮排查中，两个看似合理的猜想（序列化器问题、数据传输问题）都是靠对照实验被否掉的。

**受影响的数据**：事故期间采集的一轮压测数据已全部作废，移至 `results/invalidated/` 保存，不作为结论依据。报告中的所有数据均来自环境确认干净之后重新采集。

> 这也是本报告没有直接给出"系统容量上限是 N 个并发"的原因之一 —— 在确认测量方法可靠之前，不给出结论。
